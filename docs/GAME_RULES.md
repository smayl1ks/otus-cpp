# Runner - правила игры и числовые пороги

## 1. Суть игры

Город разбит на шестиугольники Uber H3:
- **res 9** (~170 м ребро) - «секторы», единица захвата территории;
- **res 6** (~4 км ребра, ~26 км²) - «зоны», единица подписки на карту и радар.

Бегун стартует пробежку (StartRun), в реальном времени стримит GPS-точки
батчами по WebSocket (protobuf-конверт `Envelope`), зарабатывает секторы
присутствием и замкнутыми контурами, видит других бегунов на радаре и получает
итоговую сводку (FinishRun) с очками и захваченными секторами. Пробежка,
записанная без сети, доезжает офлайн-загрузкой (init -> chunks -> commit) и
считается тем же самым финалайзером.

## 2. Античит - условия приёма точек

Батч принимается или отбрасывается **целиком** (проверки на каждую точку и на
каждую пару соседних точек):

| Условие | Порог | Статус отказа | Зачем |
|---|---|---|---|
| GPS-точность | ≤ 30 м | `GPS_ACCURACY_LOW` | точки из тоннелей/помещений с большой погрешностью не участвуют в расчётах |
| Координаты/точность конечны | NaN/Inf -> отказ | `GPS_ACCURACY_LOW` | защита от мусора в payload |
| Монотонность времени | `T_i > T_(i-1)` | `INVALID_TIMESTAMPS` | дубли и таймштампы «из прошлого» отсекаются на сегменте |
| Точка не из будущего | ≤ +5 с от сервера | `INVALID_TIMESTAMPS` | часы клиента недоверенные |
| Точка не протухшая | ≥ −24 ч от сервера | `INVALID_TIMESTAMPS` | офлайн-догрузка легальна, многодневный мусор - нет |
| Mock-геолокация | `is_mock = false` | `MOCK_DETECTED` | программная подмена геолокации |
| Размер батча | ≤ 100 точек | `BATCH_TOO_LARGE` | предел горячего пути |
| Скорость между соседними точками | ≤ 35 км/ч | `SPEED_LIMIT_EXCEEDED` | отсечение авто/самокатов/велосипедов и GPS-спуфинга |
| Телепорт | > 100 м за ≤ 1 с | `TELEPORTATION_DETECTED` | мгновенные «прыжки» сверх физики бега |

Рекомендованный интервал батчей - 5 с (`batch_interval_hint_ms`), клиент
получает его из ответа сервера.

## 3. Захват секторов

Сектор res-9 захватывается при выполнении **всех** условий:
- **≥ 3 GPS-точек** внутри гекса - «чиркнул» край одной точкой на повороте:
  гекс не засчитывается;
- **≥ 75 м** суммарной дистанции внутри гекса - защита от GPS-дрейфа на
  светофоре и вдоль границы: остановка или касательное касание сектор не
  захватывают;
- дистанция сегмента делится 50/50 между покидаемым и входным гексом.

**Замкнутые контуры (петли)**: контур с периметром ≥ 300 м, площадью
≥ 10 000 м² и замыканием ≤ 150 м растеризуется в H3 - **вся область внутри
петли захватывается целиком** (граничные + внутренние ячейки). Маршруты
«туда-обратно» вдоль одной улицы (out-and-back) имеют околонулую ориентированную
площадь и ложный захват полигона не вызывают; полигоны нормализуются к
ориентации CCW по спецификации H3.

**Скоринг**: 10 очков за каждый новый сектор (`kPointsPerHex` в `run_finalizer.cpp`).
Отменённые и невалидные пробежки сохраняются в истории с `is_valid = false` и
нулём очков.

## 4. Валидация пробежки (итог)

| Условие | Значение | Зачем |
|---|---|---|
| Мин. дистанция | 100 м | случайный запуск, «намотка» вокруг дома |
| Мин. длительность | 60 с | фарм «старт-стопами» |
| Макс. дистанция | 150 км | ультрамарафон - аномалия, сбой GPS или транспорт |
| Макс. длительность | 12 ч (43 200 с) | zombie-сессии «забыл нажать Стоп» |

Невалидная пробежка (короткая, слишком долгая, отбитая античитом до <2
живых точек) сохраняется с указанием причины (`validation_reason`), но не скорится.
Длительность сервер считает по таймштампам точек, а не по заявке клиента.

## 5. Радар и карта

- **Радар**: пинг каждой принятой батчем позиции публикуется в канал зоны
  `kazan:zone:{hex9}:radar:public` (или `...:radar:team:{team_id}` для
  team-visibility; префикс города - конфиг `city_prefix`), доставляется только
  подписанным на родительскую зону res-6. Пинг уходит только по **свежей**
  позиции (≤ 15 с от настенных часов, `freshness_window_ms`) и не для приватных
  пробежек; офлайн-догрузка старых точек радар не генерирует.
- **Подписка на карту**: клиент шлёт набор зон res-6 (до 128, идемпотентная
  замена) или bbox-совместимость со старыми клиентами (span ≤ 2° широты /
  4° долготы, обязательный отсев NaN/бесконечностей). Снапшот карты отдаётся из
  Redis-кэша (`map:zone:{h6}:…`); дыры снапшота самозалечиваются из PostgreSQL,
  на горячий путь карты PG не тратится.

## 6. Лимиты протокола и идемпотентность

| Механизм | Условие |
|---|---|
| Батч (онлайн) | ≤ 100 точек, интервал между 5 с |
| Офлайн-чанк | ≤ 1000 точек |
| Офлайн-пробежка | ≤ 43 200 точек (12 ч @ 1 Гц), длительность ≤ 12 ч |
| Дедуп батчей | по `batch_uuid` (`run:{sid}:batch:{uuid}`, NX), клейм живёт 1 ч |
| Дедуп офлайн-чанков | по `(session_id, chunk_index)`, порядок чанков любой |
| Идемпотентный старт | повторный StartRun той же сессии = resume со snapshot'ом |
| Идемпотентный финиш/коммит | summary живёт 24 ч, ретрай возвращает ту же сводку |
| Атомарность закрытия | маркер `run:{sid}:closing` (5 мин) - одна финализация на забег, PG-guard `status='active'` |
| Жизненный цикл по TTL | ключи забега (`run:{sid}:*`, `user:active_run:{id}`) живут 24 ч - мусор от оборванных сессий убирается сам |
| Соединения аккаунта | несколько живых WS на аккаунт разрешено (телефон + веб-карта); **забег не привязан к сокету** - обрыв не убивает пробежку; транспорт молчит 45 с (нет данных и pong) - соединение закрывает сервер |
| Конфликт слота | второй активный забег того же пользователя невозможен: слот `user:active_run:{id}` занят -> `ACTIVE_SESSION_EXISTS` (TTL 24 ч чистит сам) |
